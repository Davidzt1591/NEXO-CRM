# NEXO Admin Panel — Plan de Implementación Técnico

Este documento sirve como especificación técnica y guía de ejecución para implementar el **Panel de Administración** e infraestructura multi-agente en el proyecto NEXO.

---

## 1. Arquitectura General y Ruteo

La aplicación compartirá el mismo puerto y host del frontend actual:
- `/` → Dashboard de analistas (existente)
- `/admin` → Panel de Administración (nuevo, solo visible para `role === 'admin'`)

### Flujo de Acceso (Autenticación)
1. El frontend valida el token contra Supabase (`dashboard_tokens`).
2. El token retorna el rol del usuario (`admin` o `agent`).
3. El frontend de React lee este rol y renderiza condicionalmente la ruta:
   ```jsx
   if (role === 'admin') return <AdminPanel />;
   return <Dashboard />;
   ```

## 2. Modelo de Datos (Base de Datos en Supabase)

Ejecutar las siguientes sentencias SQL en Supabase para configurar la base de datos:

```sql
-- 1. Áreas de soporte
CREATE TABLE areas (
  id           BIGINT GENERATED BY DEFAULT AS IDENTITY PRIMARY KEY,
  name         TEXT NOT NULL UNIQUE,
  description  TEXT,
  welcome_msg  TEXT,
  active       BOOLEAN DEFAULT true,
  sla_minutes  INT DEFAULT 30,
  created_at   TIMESTAMPTZ DEFAULT now()
);
ALTER TABLE areas ENABLE ROW LEVEL SECURITY;
GRANT ALL PRIVILEGES ON TABLE areas TO service_role;

-- 2. Asignación de analistas a áreas y disponibilidad
CREATE TABLE analysts (
  id            BIGINT GENERATED BY DEFAULT AS IDENTITY PRIMARY KEY,
  token_id      BIGINT REFERENCES dashboard_tokens(id) ON DELETE CASCADE,
  area_id       BIGINT REFERENCES areas(id),
  display_name  TEXT NOT NULL,
  available     BOOLEAN DEFAULT false,
  last_seen     TIMESTAMPTZ,
  created_at    TIMESTAMPTZ DEFAULT now()
);
ALTER TABLE analysts ENABLE ROW LEVEL SECURITY;
GRANT ALL PRIVILEGES ON TABLE analysts TO service_role;

-- 3. Asignación de tickets a analistas
CREATE TABLE ticket_assignments (
  ticket_id    BIGINT PRIMARY KEY REFERENCES tickets(id) ON DELETE CASCADE,
  analyst_id   BIGINT REFERENCES analysts(id) ON DELETE SET NULL,
  assigned_at  TIMESTAMPTZ DEFAULT now(),
  assigned_by  TEXT DEFAULT 'auto' -- 'auto' | 'manual' | 'transfer'
);
ALTER TABLE ticket_assignments ENABLE ROW LEVEL SECURITY;
GRANT ALL PRIVILEGES ON TABLE ticket_assignments TO service_role;

-- 4. Pasos configurables del Chatbot por área (con versionado)
CREATE TABLE bot_flows (
  id           BIGINT GENERATED BY DEFAULT AS IDENTITY PRIMARY KEY,
  version_id   BIGINT DEFAULT 1,
  area_id      BIGINT REFERENCES areas(id),
  step_key     TEXT NOT NULL,
  message      TEXT NOT NULL,
  sort_order   INT DEFAULT 0,
  active       BOOLEAN DEFAULT true,
  updated_at   TIMESTAMPTZ DEFAULT now()
);
ALTER TABLE bot_flows ENABLE ROW LEVEL SECURITY;
GRANT ALL PRIVILEGES ON TABLE bot_flows TO service_role;

-- 5. Registro de adjuntos subidos a Salesforce (solo metadatos, no el archivo)
CREATE TABLE sf_attachments (
  id                      BIGINT GENERATED BY DEFAULT AS IDENTITY PRIMARY KEY,
  ticket_id               BIGINT REFERENCES tickets(id) ON DELETE CASCADE,
  sf_content_document_id  TEXT NOT NULL,
  filename                TEXT,
  mimetype                TEXT,
  size_bytes              INT,
  created_at              TIMESTAMPTZ DEFAULT now()
);
ALTER TABLE sf_attachments ENABLE ROW LEVEL SECURITY;
GRANT ALL PRIVILEGES ON TABLE sf_attachments TO service_role;

-- 6. Bitácora de Auditoría (Audit Trail) para ciberseguridad
CREATE TABLE audit_log (
  id          BIGINT GENERATED BY DEFAULT AS IDENTITY PRIMARY KEY,
  actor_name  TEXT NOT NULL,
  actor_role  TEXT NOT NULL,
  action      TEXT NOT NULL, -- 'ticket.closed', 'flow.edited', 'ticket.transferred', etc.
  target_id   TEXT,
  metadata    JSONB,
  created_at  TIMESTAMPTZ DEFAULT now()
);
ALTER TABLE audit_log ENABLE ROW LEVEL SECURITY;
GRANT ALL PRIVILEGES ON TABLE audit_log TO service_role;

-- 7. Modificaciones a tablas existentes
ALTER TABLE tickets ADD COLUMN IF NOT EXISTS area_id BIGINT REFERENCES areas(id);
ALTER TABLE bot_sessions ADD COLUMN IF NOT EXISTS flow_version_id BIGINT;
```

## 3. Seguridad y Backend (API)

### Middleware `adminOnly`
Ubicación: `backend/src/middleware/adminOnly.js`
```javascript
module.exports = function adminOnly(req, res, next) {
  if (req.user?.role !== 'admin') {
    return res.status(403).json({ error: 'Acceso no autorizado. Se requieren privilegios de Administrador.' });
  }
  next();
};
```

### Ruteo de API en Backend
Las rutas administrativas se declaran en `backend/src/routes/admin.js` y se montan bajo `/api/admin` protegidas por `adminOnly`.

## 4. Arquitectura de Sockets (Aislamiento por Salas)

Para evitar la fuga de datos y el broadcast global a analistas de diferentes áreas, el archivo `backend/src/socket.js` implementará salas de Socket.IO:

1. **Unión de salas al conectar**:
   ```javascript
   socket.join(`area:${analyst.area_id}`);
   socket.join(`analyst:${analyst.id}`);
   if (socket.user.role === 'admin') {
     socket.join('admin');
   }
   ```
2. **Emisiones de eventos dirigidas**:
   - Mensajes recibidos en tickets: `io.to('admin').to(`area:${areaId}`).emit('new-message', msg);`
   - Tickets creados: `io.to('admin').to(`area:${areaId}`).emit('ticket-created', ticket);`

## 5. Integración y Gobernanza de Datos con Salesforce

### Gestión en Memoria RAM de Medios
- Los binarios recibidos vía WhatsApp se mantendrán temporalmente en la memoria RAM del backend en Node.js.
- Se subirán directamente al Case de Salesforce mediante la API de archivos (`ContentVersion` y `ContentDocumentLink`).
- El buffer de memoria se limpia inmediatamente tras recibir confirmación de Salesforce.
- El id de documento retornado (`ContentDocumentId`) se guardará en `sf_attachments` en Supabase para referencias futuras.
- Límite estricto de tamaño de subida: **25MB**.

### Transcripción de Chat al Cierre
Al cerrar el ticket, se compilan los mensajes almacenados en la tabla `messages` asociados al `ticket_id`, se formatea la conversación en texto plano, y se añade al caso de Salesforce utilizando un `CaseComment` (`IsPublished: false`).

---

## 6. Fases de Ejecución

1. **Fase 1**: Crear tablas en Supabase, registrar rutas de API `/api/admin/*`, aplicar middleware `adminOnly`, y refactorizar Socket.IO para implementar Salas por Área.
2. **Fase 2**: Crear el frontend básico del Panel de Administración (`AdminPanel.jsx`) con gestión de analistas y áreas, incluyendo control de presencia (Socket `disconnect` cambia disponibilidad).
3. **Fase 3**: Migrar los flujos del chatbot (actualmente estáticos en `wwebjs.js`) a la base de datos `bot_flows` en Supabase. Implementar caché de 60 segundos con invalidación activa.
4. **Fase 4**: Habilitar el enrutamiento híbrido automático/manual de la cola en tiempo real con alertas SLA e interfaces diferenciadas por área para los agentes.
5. **Fase 5**: Implementar el gestor de subidas a Salesforce en RAM, transcripción al cierre del caso, reportes de performance en el admin panel, e historial en el log de auditoría.
